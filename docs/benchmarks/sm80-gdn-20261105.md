# SM80 chunked GDN prefill - CMP170HX

Measured on 2026-11-05 with one NVIDIA CMP170HX (SM80, 70 SMs, 64 GB), CUDA 12.9. Same Avalon binary, weights, input token arrays and sampling settings; the backend was selected through environment flags. Three cold-KV and three warm-KV requests per input length, sequentially. Values below are medians. Within each backend mode the model stayed loaded; expert caches were not explicitly flushed between requests. Cold KV does not mean a cold expert cache. Each mode used a separate server process. No concurrent inference or package installation during the full-model comparison.

Model: `freriadoc/Qwen3.8-Flash-Next-Avalon-GGUF`, IQ3KS, 33 main shards, plus `mtp-Qwen3.8-Flash-Next-shared-IQ3K-IQ4NL-FR65k.gguf`. The 35 downloaded files were fully rehashed. One GPU, 262144 context, batch/ubatch 4096, parallel 1, CPU threads 24, Flash Attention and CUDA Graphs enabled, K q8_0 / V q4_0, MTP draft maximum 2. Sampling: temperature 0.7, top-p 0.8, top-k 20, min-p 0, presence penalty 1.5, repeat penalty 1, seed 42, thinking disabled, 128 final output tokens.

The full-model modes ran sequentially rather than as randomized/interleaved pairs. With only three trials per input length and KV mode, these medians are descriptive measurements, not confidence intervals or a guarantee for other workloads. First-request warm-up is visible in the 8K samples: baseline cold-prefill rates were 1087.07, 1214.87 and 1208.29 tok/s; chunked rates were 1147.28, 1284.30 and 1282.35 tok/s.

## Full-model results

| Input tokens | Baseline prefill, tok/s | Chunked prefill, tok/s | Throughput gain | Baseline TTFT, s | Chunked TTFT, s | TTFT reduction |
|---:|---:|---:|---:|---:|---:|---:|
| 8192 | 1208.29 | 1282.35 | 6.13% | 7.127 | 6.750 | 5.28% |
| 32768 | 1173.50 | 1243.87 | 6.00% | 27.945 | 26.366 | 5.65% |

The table uses only cold-KV requests; every cold request reports `cache_n=0`. Warm requests reused 8188 of 8192 input tokens or 32764 of 32768, leaving four tokens to evaluate. All performance requests produced 128 final output tokens. The input-token SHA256 values match between modes.

TTFT is wall time from HTTP submission to the first nonempty text chunk. Prefill throughput comes from server timings. These are different measurements and include different overheads. Peak VRAM was approximately 59958 MiB with chunked prefill versus 59960 MiB in the baseline; this difference is noise.

Warm decode medians were 82.73 -> 83.20 tok/s at 8K and 79.13 -> 82.29 at 32K, with substantial run-to-run variation. This change targets prefill; these samples do not establish a decode gain. A separate grouped-keyhead decode experiment improved selected operator timings but reduced full-model warm decode medians to 79.27 and 76.94 tok/s. That experiment is excluded from the prefill topic and the intended release.

## Correctness and limits

The research comparison passed 103 CPU-reference cases in each of four backend modes (412 case executions), including output, committed state and replay stash checks, nonzero initial states, weak decay, odd chunk lengths, strided tensors, cache fusion and gathered state. Existing tolerances were unchanged. The prefill-only and prefill-plus-experimental-decode research variants each passed three generated-code checks (interval merge, LRU cache and Dijkstra) at roughly 26K input tokens; generated code was parsed and executed against independent assertions. These quality requests used greedy decoding (temperature 0, top-k 1, maximum 1400 output tokens), separately from the sampled 128-token performance requests above. This small sample is not a broad quality evaluation and does not prove bitwise equivalence. The 103 cases per mode comprise 75 GDN, 24 replay-stash and four cache-fusion comparisons; unchanged numerical tolerances were used. These are research-binary results, not a claim that the independently renamed upstream topic has already completed its own clean-build validation.

The optimized path uses FP16 scaled high/residual tensor-core products with FP32 state. It is opt-in upstream through `GGML_CUDA_GDN_SM80_CHUNKED=1`. This upstream topic defaults it off. A downstream launcher can opt in by setting the variable to `1`; set `0` to override such a launcher. Launcher defaults are separate from the upstream kernel change. Dispatch requires exact SM80, adequate SM/shared-memory capacity, D=128, Hk=16, Hv=48, a single sequence, aligned supported tensors and at least 128 tokens. Other hardware and unsupported shapes keep the existing path. No decode kernel is replaced.

The long-context launch fix is separate: https://github.com/freriadoc/Avalon/pull/30. The full-model research binary included that fix for both comparison modes; the prefill topic does not duplicate it. A downstream release can combine the two independent changes. A 64K-input smoke test with the research candidate completed without CUDA errors or interrupted output; it is not an additional three-run performance result.

## Raw-data provenance

The saved full-model inputs are `baseline/run.json` and `strata-prefill/run.json` in the 2026-11-05 benchmark archive, with the excluded decode comparison in `strata-all/run.json`. They record per-request timings, KV reuse, final output counts, input hashes and sampled GPU telemetry. Operator figures come from `native-recurrent-preliminary.log`, `native-mma-fp16-preliminary.log` and `native-strata-preliminary.log`; correctness logs use the `all-<mode>-GATED_DELTA_NET*` names. Those historical archive names identify the research runs, not public API names or an engine dependency. Raw files must accompany any claim requiring independent numerical reproduction; they are not embedded in this source-only topic.

## Reproduce

Build with CUDA SM80 support. Compare identical inputs with the following variable unset/`0` and then `1`, using a new server process for each mode:

```sh
GGML_CUDA_GDN_SM80_CHUNKED=1 ./llama-server ...
GGML_CUDA_GDN_SM80_CHUNKED=1 ./test-backend-ops test -o GATED_DELTA_NET
GGML_CUDA_GDN_SM80_CHUNKED=1 ./test-backend-ops perf -o GATED_DELTA_NET
```

Record raw timings, actual reused KV tokens and final output token counts. Do not count speculative draft tokens as final decode throughput. Test only one model instance at a time on this card. Results apply to this model, card and configuration; other workloads require measurement.

## Packaged build validation

The clean release build (renamed public implementation, CUDA targets 75/80/89) passed 71 CPU-reference cases with the flag off and the same 71 with it on: 69 GDN and two cache-fusion cases per mode, 142 executions total. Separate replay-stash operator fixtures belong to the research decode experiment and are not present in this release. On CMP170HX the packaged launcher completed an 8K cold/warm request pair with 128 final tokens each, reused 8188 KV tokens on the warm request, logged the active SM80 chunked path and completed a streamed tool-call/result round trip. This final smoke test is functional validation, not an additional controlled speed comparison.
